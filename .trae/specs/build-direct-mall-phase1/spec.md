# 直销（加盟）商城一期建设 Spec

## Why

厂家需要用预存锁定门店订货、用两级提成和团队业绩奖驱动门店裂变，并靠档位权益差异倒逼低档位门店升级。当前仓库为空，需要从零交付一期可上线系统（门店端微信 H5 + 厂家端 Web 后台 + 后端单体多模块 + 定时任务），支撑加盟、预存、订货、提成、业绩奖、提现、买赠、发货与全量留痕的完整闭环。

## What Changes

- 新建单体多模块工程：`mall-common` / `mall-domain` / `mall-infra` / `mall-admin`(8080) / `mall-api`(8081) / `mall-job`。
- 新建一期全部数据表（门店、档位、钱包、商品、订单、支付、提成、业绩、提现、留痕、后台配置等）与初始化数据。
- 实现门店端接口与微信 H5：注册登录、实名、加盟/升级/预存统一购买、商品三档价、购物车下单、买赠、钱包、提现、团队、业绩、记录时间线、邀请、协议。
- 实现厂家端接口与 Web 后台：工作台、门店树与详情、冻结/解冻、实名风控、等级、商品与买赠、预存活动、订单发货、提成、业绩与月结/冲正、提现审核与批次、财务对账、代客加盟、线下收款、通知、系统管理。
- 接入扫呗公众号 JSAPI 支付（4.3 / 4.10 / 4.5 / 4.8），实现验签、幂等、补偿与关单。
- 实现定时任务：支付补偿、超时关单、业绩月结、提现窗口计算、提现超期告警、对账。
- 一期不包含：小程序端、实名核验第三方接入、物流轨迹、线上退货退款、库存管理、门店员工子账号、聚合码支付。

## Impact

- Affected specs: 无（全新项目，后续二期扩展在小程序、实名核验、数据看板）。
- Affected code: 全仓库新增，包括后端六个 Maven 模块、两套前端工程、数据库初始化脚本、Docker Compose 与 Nginx 配置。

## 口径裁定（v2.9 冲突修正）

以下为需求文档 v2.9 与技术设计文档 v2.9 冲突处的最终口径，实现以此为准。

| # | 冲突点 | 裁定 |
|---|---|---|
| 1 | `level_paid_amount` 置值 vs 累计 | 以需求为准：其含义是「当前等级已付对价」，等级变更时**直接置为目标档位费**，不累加；预存且未升档时不变；建表注释同步改为「当前等级已付对价（分），等级变更置值不累加」 |
| 2 | 关单竞态两套处置 | 以 4.5 查单为关单期间的唯一真相：查单已支付 → 自动回滚取消并补记成功；**关单完成后**（payment=4/5）才到达的成功回调 → payment 回写 2、业务单置异常，进入异常单人工处置 |
| 3 | 取消接口「同事务退预存、关支付单」与 `closeBizOrder` 禁止入事务 | 改为两阶段：事务 1 条件关单 → 调 4.8 → 调 4.5 查单；确认未支付后在事务 2 退预存并置已取消；查单已支付则补记成功。纯余额订单无支付单，可直接在单事务内取消退预存 |
| 4 | 订单「异常/已退款」与「不退款、不做线上退货」 | 订货订单无异常/退款态（0 待支付 / 1 待发货 / 2 已发货 / 3 已完成 / 4 已取消）；异常单只存在于加盟/升级/预存单，门店端订单页不出现相关文案 |
| 5 | `active_mark` 唯一与多张待支付单/清理逻辑 | 以唯一约束为准：同类型最多一张未结单（含异常态）；异常单未处置前禁止新建同类型单；`closeBizOrder` 清理其余同类型待支付单仅作历史脏数据兜底，不作为常规路径 |
| 6 | 改上级「实收前可直接调整」与「一律申请审批」 | 未产生任何实收：厂家可直接调整，写 `store_parent_change(status=已通过)` 并即刻改路径；已产生实收：仅超管审批后生效；门店端只能提交申请，不能直接改 |
| 7 | 硬规则「只有 5 万档」与可配置权益开关 | `long_term` / `has_bonus` / `has_gift` 仍作为运行时事实来源，但后台保存档位时校验：**非最高 sort 档位禁止开启**这三项，防止配置破坏硬规则 |
| 8 | 协议「不落库」与「支付成功落库」 | 建单时只校验勾选、不落库；支付成功事务内写 `store_agreement`（版本/时间/IP/签署方式），代客加盟写纸质上传 |
| 9 | 提现驳回写不写 `wallet_log` | 申请、驳回、打款失败均不写 `wallet_log`（仅写 `store_event`）；仅打款成功写 `WITHDRAW, -1`；`wallet_log.biz_type` 移除 `WITHDRAW_REJECT` |
| 10 | 业绩修正的三种说法 | 结算前修正：只新增 `performance_record(ADJUST)`，不改原流水；结算后修正：只允许冲正链（原 `performance_bonus` 置 2，新增 `revision_of` 记录，`wallet_log(BONUS_REVERSAL)` 记差额）；`performance_bonus.performance` 为结算快照，不可直接编辑 |
| 11 | 留痕要求含凭证但表无字段 | `store_event` 增加 `proof_images JSON NULL`；支付原始回调报文保留在 `payment_notify_log`，仅在后台财务可查，时间线不展示原始报文 |
| 12 | 接口/字段缺失 | 新增 `GET /admin/stores/{id}/invite-qrcode`（任意门店可用）；新增业绩奖冲正接口；`payment` 增加 `offline_method`（1 现金 / 2 转账 / 3 刷卡）；`store` 增加持卡人特批字段（approved / approve_by / approve_at / proof） |
| 13 | 买赠「同一时间只能启用一条」 | 保留「每商品仅一条 `enabled=1`」的约束，切换时事务内先停用旧规则再启用新规则；一期不支持预排未来规则，需后台人工切换 |
| 14 | 升级窗口边界 | `upgrade_deadline = join_time + upgrade_days 天`；判定条件为 `now <= upgrade_deadline`（含到期时刻），到期之后走预存路径 |
| 15 | 活动限次是否统计补差单 | 只统计该门店在该活动下已支付的 `recharge_order`；窗口期内走 `join_order(type=2)` 的补差购买不计入活动参与次数，活动页对应档位显示「按差额支付」或引导升级 |
| 16 | 超期升更高档按全额收款 | 按需求执行：超期后升档一律全额收款，旧对价不抵扣、余额保留；后台建单页明确提示「超期升档需全额支付」 |
| 17 | 附录 A 与 3.7 的规则示例档位不同 | 验收以 3.7 的规则结构为准（阈值与比例均后台可配）；附录 A 仅演示算法，其 10 万/20 万阈值不用于验收 |

## ADDED Requirements

### Requirement: 工程骨架与基础设施
系统 SHALL 以 JDK 17 + Spring Boot 3.2 + MyBatis-Plus 3.5 提供单体多模块工程，统一返回体 `{code,msg,data}`、全局异常、错误码分段（1xxxx 通用 / 2xxxx 门店 / 3xxxx 订单 / 4xxxx 钱包提现 / 5xxxx 支付），并通过 Docker Compose 部署 Nginx + mall-admin + mall-api + mall-job + MySQL 8 + Redis 7。

#### Scenario: 服务启动与健康
- **WHEN** 执行 `docker compose up`
- **THEN** mall-admin 监听 8080、mall-api 监听 8081、mall-job 以 `job` profile 启动，Nginx 将 `/admin/*` 与 `/api/*` 分别转发

#### Scenario: 统一错误响应
- **WHEN** 接口发生业务异常
- **THEN** 返回对应分段错误码与中文提示，HTTP 状态与响应体结构一致

### Requirement: 门店注册、登录与实名
系统 SHALL 支持手机号 + 短信验证码注册登录；扫码注册自动绑定邀请人上下级并生成物化路径 `path`（始终以 `/` 结尾）；未实名的门店不能加盟、不能下单；未加盟只能浏览、不能下单；一期实名只采集留档（AES 加密身份证、银行卡，SHA-256+盐做重复比对），不接第三方核验但预留接口。

#### Scenario: 扫码注册绑定上级
- **WHEN** 新用户通过邀请码注册
- **THEN** 门店 `parent_id`、`path` 正确写入，登录后可浏览但不可下单

#### Scenario: 重复人员标记
- **WHEN** 同一身份证号/执照号/手机号注册出第二个门店
- **THEN** 门店被标记 `duplicate_flag` 并记录 `duplicate_of`，后台可见待核实

### Requirement: 档位与统一购买路径判定
系统 SHALL 由后端按文档 3.3 判定表统一决定加盟/升级/预存路径，档位高低按 `sort` 比较而非金额：未加盟（`level_id=0`）生成加盟单（type=1）全额收款；窗口期内（`now <= upgrade_deadline`）且目标 `sort` 更大生成补差单（type=2）并收 `目标档位费 − level_paid_amount`；其余情况生成预存单全额收款。`level_paid_amount` 表示当前等级已付对价，等级变更时直接置为目标档位费、不累加；预存路径不校验已缴金额；补差额 ≤ 0 时拒绝并记告警日志。

#### Scenario: 1 万档门店窗口期升 5 万
- **WHEN** 门店已缴 10000 分对应 1 万档，在 `upgrade_deadline` 之前（含到期时刻）选择 5 万档
- **THEN** 生成补差单，应收金额为 5 万档费 − 10000，支付后等级与 `level_paid_amount` 置为 5 万档费

#### Scenario: 窗口期到期
- **WHEN** 当前时间晚于 `upgrade_deadline`
- **THEN** 即使选择更高档位也走预存单全额收款，不生成补差单

#### Scenario: 5 万档门店买 3 万档
- **WHEN** 5 万档门店选择 3 万档
- **THEN** 生成预存单按 3 万全额收款，预存入账，等级仍为 5 万档、`level_paid_amount` 不变

#### Scenario: 未加盟门店购买
- **WHEN** `level_id=0` 的门店调用统一购买接口且已实名、已勾选协议
- **THEN** 生成加盟单，支付成功后写入等级、窗口期、预存余额、档位变更流水与协议签署记录

### Requirement: 预存活动与常驻预存
系统 SHALL 提供常驻「预存/升级」入口（列出三档、金额等于加盟费、可重复参与）以及可选预存活动（上下架、有效期、适用档位、每人限 N 次）；活动限次只统计该门店该活动已支付的预存单，窗口期内走补差单的购买不计入；活动页对会触发补差的档位显示「按差额支付」或引导升级。

#### Scenario: 活动限次
- **WHEN** 门店在某活动下已有 1 笔已支付预存单且限次为 1
- **THEN** 再次创建该活动预存单被拒绝

#### Scenario: 补差不消耗活动次数
- **WHEN** 窗口期内门店通过活动页选择更高档位
- **THEN** 生成补差单（join_order type=2），该笔不占用活动限次

#### Scenario: 活动下架
- **WHEN** 活动状态为下架
- **THEN** 常驻预存入口仍可用，仅活动不可选

### Requirement: 钱包双账户
系统 SHALL 维护预存账户与佣金账户两个独立子账户：预存只能订货、佣金只能提现；所有余额变动经 `WalletService` 写 `wallet_log`（记录变动前后余额、业务单号、来源、操作人、凭证），使用 `SELECT ... FOR UPDATE` 行锁 + `version` 兜底；下单只扣预存，不足部分走微信支付；佣金余额允许为负并在后续入账时先抵扣。

#### Scenario: 预存不足混合支付
- **WHEN** 订单总额大于预存余额且门店选择微信补足
- **THEN** 预存部分扣减并写流水，差额生成支付单走 JSAPI，支付成功后订单进入待发货

#### Scenario: 余额只能按用途使用
- **WHEN** 门店尝试用佣金余额下单
- **THEN** 系统拒绝并提示佣金账户不可用于订货

### Requirement: 两级提成
系统 SHALL 按厂家实收金额计算两级提成（一级 10%、二级 3%，后台可调，向下取整到分）：首次加盟任意档位上级均可拿；补差/预存/线下收款/订单在线支付仅 5 万档受益人可以拿；未加盟门店与厂家不参与；用预存余额订货不产生提成；受益人冻结时照常入账；同一业务单同一受益人只入账一次。

#### Scenario: 1 万档上级拿首次加盟提成
- **WHEN** 下级新加盟支付 3 万，其一级上级当前为 1 万档
- **THEN** 上级佣金账户入账 3000 元（按比例向下取整到分），二级上级按 3% 入账

#### Scenario: 重复回调幂等
- **WHEN** 同一支付成功回调重复到达 10 次
- **THEN** 提成、业绩、余额只入账 1 次

### Requirement: 团队业绩奖与冲正
系统 SHALL 于次月 1 日对「上月末最后一天为 5 万档且享业绩奖」的门店，按结算时的子树（自己 + 整棵下级）汇总当月厂家实收业绩，按 `min_amount <= 业绩` 的最大档位比例全额累进计算奖励并入佣金账户；被结算月份内存在任何冻结区间则不结算且不补发；业绩未命中任何档位不写奖励记录（冲正为 0 除外）；结算前修正只新增 `ADJUST` 业绩流水，结算后修正只能走冲正链；`performance_bonus.performance` 为结算快照，不允许直接编辑。

#### Scenario: 附录 A 第 7 步
- **WHEN** B 团队当月业绩为 110500 元且命中 0.5%
- **THEN** B 佣金账户增加 552.50 元，`performance_bonus` 写入快照与规则命中信息

#### Scenario: 冻结月份不结算
- **WHEN** 门店在结算月份内存在任何冻结区间
- **THEN** 当月不生成业绩奖，解冻后也不补发

#### Scenario: 结算前修正
- **WHEN** 当月尚未月结，后台修正某门店业绩
- **THEN** 新增一条 `performance_record(ADJUST, source=2)`，原流水不变，月结按汇总后的业绩计算

#### Scenario: 结算后冲正
- **WHEN** 对已入账月份修正业绩
- **THEN** 原奖励记录置 `status=2`，新增 `revision_of` 指向原记录的冲正记录，`wallet_log(BONUS_REVERSAL)` 只记修正后与原始的差额，备注带原记录 id

### Requirement: 提现
系统 SHALL 仅允许每月 15 日与月末最后一天 0:00–23:59 提交提现申请，最低金额后台可配（默认 100 元），无上限、无手续费；申请时校验可用余额 `commission_balance − frozen_amount ≥ amount` 并冻结金额；审核通过后进入待打款，生成批次、导出清单、线下转账后标记已打款（上传截图）或打款失败（填原因并解冻退回）；状态机为待审核 → 待打款 → 已打款 / 已驳回 / 打款失败；门店只能绑定一张收款卡且持卡人须与实名一致，不一致仅允许后台特批代改并留痕。

#### Scenario: 非窗口期申请
- **WHEN** 门店在非 15 日且非月末的日子提交提现
- **THEN** 系统拒绝并提示可申请日期

#### Scenario: 驳回不写余额流水
- **WHEN** 后台驳回一笔提现申请
- **THEN** 仅解冻并写 `store_event(WITHDRAW_AUDIT)`，不写 `wallet_log`

#### Scenario: 打款失败恢复额度
- **WHEN** 后台将某笔提现标记为打款失败并填写原因
- **THEN** 冻结金额退回、可用余额恢复，门店收到通知并可在下个窗口改卡重提

### Requirement: 商品、三档价与买赠
系统 SHALL 支持商品分类、商品、多规格（瓶/箱 + 折算瓶数）、每个规格 V1/V2/V3 三档价；未配置某档位价格时该档位不可购买（前台置灰、后端拒绝）；仅 5 万档且商品开启 V3 买赠时按「门槛（按瓶折算）× 倍数」赠送同商品瓶数，赠品 0 元、随主货发出、不计订单金额/业绩/提成；同一商品仅保留一条启用规则，切换时先停用旧规则再启用新规则，一期不支持预排未来规则。

#### Scenario: 买多送多
- **WHEN** 5 万档门店购买 2 箱（1 箱 12 瓶）且规则为满 12 瓶送 3 瓶
- **THEN** 订单生成 6 瓶 0 元赠品行，主货金额不变

#### Scenario: 非 5 万档无赠品
- **WHEN** 1 万档或 3 万档门店下单同一商品
- **THEN** 不生成赠品行

#### Scenario: 规则切换
- **WHEN** 后台启用新买赠规则
- **THEN** 同事务内先停用该商品旧规则再启用新规则，任一时刻最多一条 `enabled=1`

### Requirement: 订单与发货
系统 SHALL 支持购物车、结算、预存抵扣 + 微信补足、下单 10 分钟未支付自动取消并退回已扣预存；订货订单状态只包含 0 待支付 / 1 待发货 / 2 已发货 / 3 已完成 / 4 已取消，不设异常/退款态；发货支持物流（公司 + 单号）或其他（上传凭证），门店确认收货后完成；一期不做物流轨迹、退款与库存。

#### Scenario: 纯余额订单
- **WHEN** 订单金额可由预存全额抵扣
- **THEN** 不创建支付单，扣减预存后直接进入待发货

#### Scenario: 超时取消退款
- **WHEN** 订货单创建后 10 分钟未支付，经 4.5 查单确认未支付
- **THEN** 支付单关闭、订单取消，已扣预存全额退回并写 `ORDER_REFUND` 流水与取消事件

#### Scenario: 发货两种方式
- **WHEN** 厂家选择物流发货或上传其他凭证
- **THEN** 订单记录对应的物流单号或凭证，门店端仅查看展示信息

### Requirement: 支付与关单
系统 SHALL 接入扫呗 4.3 公众号 JSAPI（验签、金额比对、幂等、4.10 回调 + 4.5 查单兜底、4.8 关单）；关单统一走 `closeBizOrder`，不得在支付成功事务内调用；关单期间以 4.5 查单为唯一真相，查单已支付则回滚取消并补记成功；已关闭/已退款后到达的成功回调将支付单回写成功、业务单转异常并告警；取消订单接口采用两阶段流程（先关单查单、确认未支付后再退预存）。

#### Scenario: 关单后回调成功
- **WHEN** 支付单已完成关闭后又收到成功回调
- **THEN** 支付单置成功、业务单置异常，进入异常单列表等待人工处置，不丢钱

#### Scenario: 关单时查单已支付
- **WHEN** 关单流程调用 4.5 查单返回已支付
- **THEN** 回滚取消，按支付成功补记业务，订单不再取消

#### Scenario: 取消订单
- **WHEN** 门店取消未支付订单
- **THEN** 先关单并查单；确认未支付后才在同一事务内退回预存并置已取消

### Requirement: 异常单处置
系统 SHALL 对「已收款但业务前置校验失败」的加盟单/补差单/预存单提供补开通、原路退款、仅关闭三种处置，均留操作人与时间；补开通前校验门店当前档位（不低于目标则只入余额、不改档位与已缴对价）与业绩月份是否已结算；原路退款不写余额流水，只写退款支付状态与 `PAY_REFUND` 事件；异常单未处置前禁止该门店新建同类型单据。

#### Scenario: 补开通不改低已缴对价
- **WHEN** 异常单目标档位不高于门店当前档位时选择补开通
- **THEN** 仅将金额入预存余额，不写档位变更流水、不覆盖 `level_paid_amount`

#### Scenario: 异常未处置阻止新单
- **WHEN** 门店存在一张未处置的异常加盟单
- **THEN** 再次创建加盟/升级单被拒绝并提示先联系厂家处理

### Requirement: 代客加盟与线下收款
系统 SHALL 区分两种线下场景：未加盟门店走代客加盟（生成加盟单 + 线下支付单并记录收款方式，复用 JOIN 的等级、已缴对价、窗口期、预存、业绩与提成逻辑，强制上传证件照与已签署协议扫描件，协议签署方式记为纸质上传）；已加盟门店走线下收款（按判定表生成补差单或预存单，金额由系统计算、后台只读，记录实际收款时间与收款方式）；余额调整不计业绩不计提成但必须填原因。三类操作统一通过 `PurchaseService.createOrder()` 建单并复用幂等逻辑。

#### Scenario: 招商会代客加盟
- **WHEN** 厂家为未加盟门店 E 录入 5 万档现金收款并上传凭证、证件、纸质协议
- **THEN** E 等级开通、预存 +5 万、业绩与首次加盟提成按 JOIN 规则计算，协议留痕为纸质上传

#### Scenario: 线下收款不能走代客加盟
- **WHEN** 门店已加盟，后台尝试代客加盟
- **THEN** 接口拒绝并提示只能走线下收款或预存/升级

### Requirement: 冻结门店
系统 SHALL 支持厂家冻结/解冻门店：冻结期间禁止登录、下单、预存、加盟升级、修改资料与银行卡，禁止新提现申请但已提交申请继续审核打款，禁止生成邀请二维码；下级付款产生的提成照常入账；被结算月份内存在冻结区间则不结算业绩奖；下级关系与架构保持不变；解冻后恢复全部操作。

#### Scenario: 冻结中提成入账
- **WHEN** 冻结门店的下级完成支付
- **THEN** 该冻结门店的佣金账户照常入账并写流水

### Requirement: 全量留痕与时间线
系统 SHALL 对所有与钱相关的动作写入只追加不修改的 `store_event`（时间、门店、事件类型、金额、业务单号、操作人/来源、凭证图片），并在门店详情与门店端时间线按类型（加盟/预存/订货/提成/业绩/提现）筛选展示；资金与档位变更必须与业务数据在同一事务内写入事件；已入账数据更正走冲正并保留原记录；支付原始回调报文仅保留在后台财务，不进入门店时间线。

#### Scenario: 下单与提成可追溯
- **WHEN** 完成一笔订货支付并产生上级提成
- **THEN** 门店时间线中可查到订单支付、余额抵扣、赠品与提成到账记录，金额与业务表一致

### Requirement: 团队与数据隔离
系统 SHALL 让门店只能访问自己与整棵下级子树的架构与业绩，提成明细只展示 `to_store_id = 自己` 的记录；子树查询基于登录时缓存的 `path` 前缀展开；改上级按「实收前厂家可直接调整、实收后仅超管审批」执行，审批前校验目标上级 `path` 不得以本门店 `path` 开头，生效时事务内批量更新子树路径并清理祖先缓存；业绩流水按支付时点留存，团队业绩奖按结算时子树计算。

#### Scenario: 越权访问兄弟门店
- **WHEN** 门店请求非自己子树的订单或团队数据
- **THEN** 系统拒绝

#### Scenario: 改上级成环
- **WHEN** 尝试把门店挂到自己的下级之下
- **THEN** 操作被拒绝，不产生路径环

#### Scenario: 实收前直接改上级
- **WHEN** 门店尚无任何实收，厂家调整其上级
- **THEN** 直接生效并写 `store_parent_change` 与 `store_event`，子树路径同步更新

### Requirement: 后台管理与对账
系统 SHALL 提供工作台、门店管理（树、详情、新增、改上级、冻结、重置手机号、任意门店邀请二维码）、实名风控、等级管理（保存时校验非最高档不得开启长期提成/业绩奖/买赠）、商品与买赠、预存活动、订单与发货、提成流水、业绩规则与月结/修正/冲正、提现审核与批次导出、财务（预存/佣金流水、支付流水、线下收款、余额调整、对账）、通知与短信模板、管理员角色与操作日志；对账三条断言必须恒成立：`deposit_balance` 等于预存流水净额、`commission_balance` 等于佣金流水净额、`frozen_amount` 等于待审核+待打款提现金额。

#### Scenario: 对账无差异
- **WHEN** 存在在途提现时执行对账
- **THEN** 三条断言差额均为 0

#### Scenario: 权益开关越权配置
- **WHEN** 后台尝试给非最高档位开启 `long_term` / `has_bonus` / `has_gift`
- **THEN** 保存被拒绝并提示仅最高档位可开启

### Requirement: 定时任务
系统 SHALL 提供支付补偿（每分钟查询中间态支付单调 4.5）、超时关单（每分钟关闭超 10 分钟未付的订货单/加盟单/预存单）、业绩月结（每月 1 日 01:30，按 `(store_id, month)` 幂等，失败清单告警）、提现窗口计算、提现批次超 7 天未打款告警、每日对账。

#### Scenario: 月结重跑
- **WHEN** 首次月结在第 300 家门店失败后重跑
- **THEN** 已入账门店跳过，剩余门店补齐，无重复发放

### Requirement: 非微信环境与非功能约束
系统 SHALL 在微信外打开门店端时展示「请在微信中打开」引导页（含复制链接），支付环节二次拦截；识别 Windows/Mac 微信 UA 同样引导至手机；金额以分存储、比例向下取整；验证码 5 分钟有效且同号 60 秒限流；支付密钥仅走环境变量；上传文件限定类型与大小并按日期分目录存放至 OSS。

#### Scenario: PC 浏览器打开门店端
- **WHEN** 用户在非微信浏览器访问门店端页面
- **THEN** 展示引导页并可复制链接，绕过引导后支付请求被拦截
